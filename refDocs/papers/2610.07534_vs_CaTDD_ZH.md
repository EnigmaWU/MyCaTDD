## 1. 执行摘要

EPIC 与 CaTDD 面对的是同一种风险，但它们位于开发生命周期的不同位置。

EPIC 要回答：

> 规范、计划和任务这些制品共同构成的集合，是否已经足够清晰、完整、一致且 可验证，使实现智能体不必静默补写缺失意图？

CaTDD 要回答：

> 有来源依据的意图是否已经被转换为可追溯、可测试、可执行的义务，并且实现 是否只在具备 RED/GREEN 证据和审查门禁的条件下推进？

二者是互补关系：

- EPIC 主要是一套**制品质量透镜与评估框架**。
- CaTDD 主要是一套**执行方法、验证语言与生命周期控制系统**。
- EPIC 判断意图是否已经被足够明确地表达。
- CaTDD 控制明确表达的意图是否经历设计、测试、实现、审查和关闭。

最关键的结论不是 CaTDD 需要增加 40 个新复选框，而是 CaTDD 需要增加一种 治理对象：

> 在把“可测试性”当作就绪证据之前，必须先判断整个规范制品集合的质量是否 充分。

一个 AC 可以完全可测试，却仍然不完整。一个计划可以前后一致，却实现了错误 的范围。一个测试可以全部通过，却只验证了从未被正确表达的义务。TDD 保证的是 实现相对于已表达意图的纪律，并不独立保证已表达意图本身足够充分。

因此，CaTDD 可增加三项高价值能力：

1. **制品集合充分性门禁**：把 Story、User Guide、Architecture、Detail Design、Verification Design、Plan 与 Tasks 作为一个语义整体审查，而不是 让每个文档孤立通过。
2. **统一语言与规范语气控制**：统一定义术语、ID、`MUST` / `MAY` / `MUST NOT`、范围边界与完成谓词，防止下游制品重新解释上游意图。
3. **EPIC 质量债务与风险分级**：把部分满足或不适用的实践记录为有责任人 的显式债务，而不是简单分成“通过”或“阻塞”两类。

CaTDD 在执行设计、测试点发现、语义 RED、运行环境证据归属和生命周期治理方面 已经强于 EPIC。因此，正确方向是把 EPIC 作为**执行前的规范质量透镜**，而不是 用它替换 CaTDD 的测试驱动执行模型。

## 2. EPIC 真正贡献了什么

### 2.1 质量单位发生变化

EPIC 的核心理论贡献，是把规范质量的分析单位从“单条需求”提升为“制品集合”。

传统需求工程关注一条需求是否无歧义、单一且可验证。EPIC 保留这些要求，但增加：

- 实现所依赖的假设和约束。
- 必需行为与设计、实现决策之间的分离。
- 显式的计划和任务信息。
- 规范、计划、任务三者之间的一致性。

EPIC 的十个质量维度是：

| EPIC 类别 | 维度 | 核心问题 |
| --- | --- | --- |
| Expressive（表达） | Unambiguous、Singular、Verifiable | 系统必须做什么，怎样才算完成？ |
| Precise（精确） | Dependency Control、Complete | 在什么假设和范围内完成？ |
| Interpretable（可解释） | Conforming、Consistent、Comprehensible | 人与智能体是否会得到相同解释？ |
| Compartmentalized（分区） | Scope Discipline、Implementation-Planning Information | 产品意图与实现指导是否分离但又能追溯？ |

### 2.2 EPIC 的 40 项实践

#### Expressive（表达）

- E1 Unambiguous（无歧义）
  - E1.1 主动请求澄清。
  - E1.2 量化或可测量的需求。
  - E1.3 受控词汇与枚举定义。
  - E1.4 规范语气与结构的一致性。
  - E1.5 显式范围和验证边界。
- E2 Singular（单一性）
  - E2.1 原子的功能与行为陈述。
  - E2.2 单一的架构与设计事实。
  - E2.3 独立记录风险、假设、边界情况和约束。
  - E2.4 独立的定义、场景和关系陈述。
  - E2.5 独立的安全与隐私属性。
- E3 Verifiable（可验证）
  - E3.1 验证标准与可测量结果。
  - E3.2 验证场景与验证方法。
  - E3.3 完整的验证覆盖范围。
  - E3.4 验证完成条件和就绪判断。

#### Precise（精确）

- P1 Dependency Control（依赖控制）
  - P1.1 明确声明假设与依赖。
  - P1.2 明确约束与范围边界。
  - P1.3 需求与任务层面的依赖及风险可追溯。
  - P1.4 依赖验证与失败模式处理。
- P2 Complete（完整）
  - P2.1 功能与用户需求覆盖。
  - P2.2 异常行为与范围定义。
  - P2.3 技术、运行和质量约束。
  - P2.4 依赖与交付计划。
  - P2.5 规范完整性管理。

#### Interpretable（可解释）

- I1 Conforming（符合约定）
  - I1.1 标准化的文档结构。
  - I1.2 稳定、唯一的需求标识符。
  - I1.3 显式声明并执行模板约定。
- I2 Consistent（一致）
  - I2.1 标准化术语与概念定义。
  - I2.2 统一的标识符与记号。
  - I2.3 跨制品对齐与可追溯性。
  - I2.4 一致的组织结构。
- I3 Comprehensible（可理解）
  - I3.1 结构化的文档组织。
  - I3.2 跨文档上下文与导航。
  - I3.3 辅助理解的示例与说明。

#### Compartmentalized（分区）

- C1 Scope Discipline（范围纪律）
  - C1.1 面向行为的产品规范。
  - C1.2 产品关注点与项目关注点分离。
  - C1.3 可追溯地过渡到实现。
- C2 Implementation-Planning Information（实现计划信息）
  - C2.1 技术上下文与实现基础。
  - C2.2 实现计划与任务组织。
  - C2.3 需求到实现的可追溯性。
  - C2.4 实现数据模型与演进计划。

### 2.3 实证基础与边界

EPIC 的研究范围远超一般设计论文：

- 发现 850 个候选代码仓库。
- 筛选 206 个仓库。
- 最终分析 114 个使用 AI 智能体规范制品的开源仓库。
- 从 5,675 个编码片段中推导出 40 项实践。
- 交叉核对 30 份灰色文献。
- 由 15 名有 SDD 经验的专业人员评价框架。
- SonarQube 分析覆盖 100 个仓库，GitHub 活跃度分析覆盖 109 个仓库。

论文报告了规范质量与仓库结果之间的一些关联：

- 高质量组的 bug 修复提交占比为 11.8%，低质量组为 20.4%。
- 高质量组每 KLOC 的中位圈复杂度低 15.4%。
- 高质量组每 KLOC 的中位漏洞密度约低一半，但全区间相关性并不显著。
- 高质量组的中位贡献者数量为 12.5，低质量组为 3。
- Pull Request、合并 PR、Issue 和提交数量也更高。

这些结果值得重视，但不能证明因果关系。仓库成熟度、团队规模、语言、项目类型、 既有贡献活跃度和文档投入都可能是混杂因素。论文本身也明确把结果描述为探索性、 观察性研究。

实践结论是：

> EPIC 提供的是一套有实证基础的质量诊断词汇，而不是已被证明必须普遍遵行的 法规。

## 3. 结构分类：EPIC 与 CaTDD

```text
┌──────────────────────────────────────────────────────────────┐
│ EPIC                                                         │
├──────────────────────────────────────────────────────────────┤
│ Specification + Plan + Tasks                                 │
│ E: Expressive    -> 含义、单一性、可验证性                   │
│ P: Precise       -> 依赖、完整性、约束                       │
│ I: Interpretable -> 约定、一致性、可理解性                   │
│ C: Compartment.  -> 产品意图与实现计划分离                   │
│                                                              │
│ 0-3 维度评分；40 项实践；以制品证据为依据                    │
└───────────────────────────┬──────────────────────────────────┘
                            │ 互补的质量透镜
                            ▼
┌──────────────────────────────────────────────────────────────┐
│ CaTDD 与 Px-SpecFlow                                         │
├──────────────────────────────────────────────────────────────┤
│ Story 意图 -> README SPEC -> 详细设计                        │
│ -> discovery ledger -> US/AC/TP/TC -> RED/GREEN              │
│ -> Review -> Commit -> Closure                               │
│                                                              │
│ F: Contract      -> P0 Typical / Edge / Misuse / Fault       │
│ Model: P1        -> State / Capability / Interaction / Race  │
│ Envelope: P2     -> 质量运行包络                             │
│ Learning: P3     -> Demo 与入门验证                          │
│                                                              │
│ TestEvidenceChain、运行证据、确定性门禁                      │
└──────────────────────────────────────────────────────────────┘
```

EPIC 与 CaTDD 生命周期的大致对应关系如下：

| EPIC 关注点 | 主要 CaTDD 位置 | 当前强度 |
| --- | --- | --- |
| 表达性需求 | Story 模板、AC ledger、`SPEC_reviewUserStory` | 强，但单一性措辞和规范语气尚未完全强制 |
| 依赖与完整性 | Scope、Risks、Assumptions、设计面、discovery ledger | 强 |
| 可解释性 | ID、模板、追溯链接、审查门禁 | 结构强，项目级术语表较弱 |
| 产品与实现分离 | Flow orientation、Story/Design/Tasks 分层 | 强 |
| 验证与完成 | Discovery Gate、审查契约、RED/GREEN、关闭门禁 | 比 EPIC 的纯审计模型更强 |

更深层的关系不是“EPIC 补上 CaTDD 缺失的实践”，而是：

- EPIC 提供**上游规范制品集合的质量谓词**。
- CaTDD 提供**消费该谓词的可执行控制系统**。

## 4. SAME：EPIC 与 CaTDD 的共同基础

### 4.1 拒绝智能体的静默假设

两个框架都认为：智能体会用看似合理、但未经授权的决定填补需求空白。

CaTDD 的通用 `ONE-MORE-THING` 规则和 `QUESTION` ledger，防止未解决的来源、 oracle、范围或所有权问题被静默转化为行为。EPIC 的显式澄清和未决问题标记， 在规范层表达了相同不变量。

共同原则是：

> 沉默不等于已经作出的规范决定。

### 4.2 可测量或可观测的完成

EPIC 要求验证标准、验证方法、覆盖范围和完成条件。CaTDD 要求有来源依据的 oracle、验证方法、类别覆盖和就绪门禁。二者都拒绝把实现智能体的自我声明 当作“完成”。

CaTDD 进一步区分：

- AC：调用方或用户价值视角。
- TP：开发者防御性技术义务。
- TC：可执行验证制品。
- RED：因预期语义原因失败。
- GREEN：可执行义务通过。
- `ready_for_implementation`：当前实现范围就绪，不等于发布就绪。

### 4.3 构造式追溯

EPIC 强调稳定 ID 和跨制品追溯。CaTDD 已经定义：

```text
Source -> Rule / Invariant -> TP -> Oracle -> Category
       -> US / AC / TC -> RED / GREEN Evidence
```

CaTDD 在这里更强，因为它不仅追溯文档元素，还追溯防御性测试理由和可执行证据。

### 4.4 明确范围与异常行为

EPIC 的范围排除、异常行为和技术/运行约束，与 CaTDD 的以下机制重合：

- Story `Scope` 与 `Non-goals`。
- `Typical`、`Edge`、`Misuse`、`Fault` 分类。
- `REFERRED` 与 `EXCLUDED` discovery disposition。
- Error、Resource、Compatibility、Security、Diagnosis 设计面。

两个框架都承认：边界未定义不等同于已经决定该边界不适用。

### 4.5 升级给人类，而不是降低标准

EPIC 倾向于保留未决澄清，而不是让生成器自行发明策略。CaTDD 的有限重试、 `ONE-MORE-THING`、审查 verdict 和人工升级机制，把同一安全策略落成了操作流程。

### 4.6 分离产品意图与实现指导

EPIC 的 Compartmentalized 类别把行为产品需求和计划、任务信息分离。CaTDD 已经区分：

- Intent clearing（意图澄清）。
- Requirement-oriented（需求导向）。
- Design-oriented（设计导向）。
- Implementation-oriented（实现导向）。

TestEvidenceChain 与 TASKS 制品再把这些层次连接起来，而不把它们混成一团。

## 5. DIFF：两个框架的互补差异

| 维度 | EPIC | CaTDD |
| --- | --- | --- |
| 核心制品 | Specification、Plan、Tasks | Story、README SPEC、Discovery Ledger、测试骨架、测试与代码 |
| 主要目的 | 评估制品质量 | 控制从设计到代码的执行 |
| 分析单位 | 制品集合 | 来源到证据链 |
| 评估方式 | 10 个 0-3 维度、40 项实践 | 聚焦式门禁、verdict、disposition 与测试证据 |
| 需求视角 | 主要是用户/系统义务 | AC 价值视角 + TP 防御视角 |
| 缺失质量的处理 | rubric 证据与适用性 | `QUESTION`、`EXCLUDED`、`REFERRED`、`GAP`、`BLOCKED` |
| 产品/实现拆分 | Specification vs. Plan/Tasks | Intent、Requirement、Design、Test Design、Implementation orientation |
| 完成证据 | 规范中的标准和完成条件 | 语义 RED/GREEN、审查门禁、运行与测试证据 |
| 智能体安全 | 澄清标记与不完整规范识别 | 通用人工升级不变量与 Loop Guard |
| 主要优势 | 覆盖广、可比较、有实证基础 | 可执行、可测试、追溯深、生命周期控制强 |
| 主要风险 | 文档负担、等权评分、观察性证据 | 局部门禁可能共同遗漏上游语义不充分 |

### 5.1 质量透镜与控制闭环

EPIC 是透镜：告诉开发者应检查什么，以及如何评分。

CaTDD 是控制闭环：告诉开发者与智能体下一步能做什么、必须具备什么证据， 以及何时必须停止。

组合后的关系是：

```text
EPIC 质量证据 -> CaTDD 门禁决策 -> 有界重工或人工升级
```

只有维度分数而没有门禁，不会改变任何工程行为；只有门禁而没有质量词汇， 则可能不知道门禁究竟为何应该失败。

### 5.2 外部制品集合与注释鲜活执行模型

EPIC 把规范、计划和任务看作文档流水线。CaTDD 把一部分设计意图直接放入 测试注释，并让 discovery ledger 靠近验证证据。

这不是冲突：

- EPIC 在实现前评估上游文档。
- CaTDD 在实现开始后保持可执行设计意图。
- 注释鲜活机制缩短上下文距离。
- EPIC 的制品集合视角能发现单靠就地注释无法发现的跨文档遗漏。

### 5.3 需求质量与测试充分性不是同一件事

EPIC 不设计测试，它只判断需求和计划是否足够清晰、可执行。

CaTDD 当前也没有对完整制品集合进行整体质量评分。它判断 AC 是否能转换为 TP/TC，以及设计来源是否支持这些义务。

因此，可能出现“测试套件内部非常严谨，但共同验证的是一个范围错误、表达不完整的 制品集合”的情况。这是最重要的缺口。

### 5.4 Rubric 与工程方法

EPIC 相对工具中立，可应用于扁平需求文档、GitHub Spec Kit、OpenSpec 或其他 SDD 流水线。CaTDD 则对生命周期、类别、测试结构、追溯和证据有明确主张。

EPIC 可以为 CaTDD 提供质量词汇；CaTDD 可以为 EPIC 提供执行和领域级严谨性。

## 6. 当前 CaTDD 对 EPIC 40 项实践的逐项审计

图例：

- **Covered（已覆盖）**：CaTDD 有明确实践或等价不变量。
- **Partial（部分覆盖）**：关注点存在，但执行或制品覆盖不均衡。
- **Gap（缺口）**：尚无持久表示或门禁。

| EPIC 实践 | 当前 CaTDD 证据 | 状态 |
| --- | --- | --- |
| E1.1 主动澄清 | `ONE-MORE-THING`、QUESTION ledger、`ASK` | 已覆盖 |
| E1.2 可测量需求 | AC review、质量场景、阈值、精确谓词 | 已覆盖 |
| E1.3 受控词汇与定义 | Input/Output Dictionary、Category Semantics，但无统一语言门禁 | 部分覆盖 |
| E1.4 规范语气与结构一致 | GIVEN/WHEN/THEN 与模板，但无 modal-language 规则 | 部分覆盖 |
| E1.5 范围与验证边界 | Scope/Non-goals、TestScope、`EXCLUDED`/`REFERRED` | 已覆盖 |
| E2.1 原子功能陈述 | 模板要求一个场景一个行为，但审查强制执行不稳定 | 部分覆盖 |
| E2.2 单一架构/设计事实 | 架构、详细、状态、错误和质量设计表格 | 部分覆盖 |
| E2.3 独立风险/假设/边界项 | Risks、Assumptions、Question Ledger、P0 分类 | 已覆盖 |
| E2.4 单一定义/场景/关系 | Data Dictionary、Behavior Scenarios、TP ledger | 已覆盖 |
| E2.5 独立安全/隐私属性 | Security Design、宪法不变量、P2 Security | 已覆盖 |
| E3.1 验证标准与结果 | AC、TP oracle、反测试演戏断言 | 已覆盖 |
| E3.2 验证场景与方法 | Discovery Ledger 与 Verification Design 分工 | 已覆盖 |
| E3.3 验证覆盖完整性 | 系统化 sweep 与 coverage matrix，但只限声明范围 | 部分覆盖 |
| E3.4 完成与就绪 | `ready_for_implementation`、review verdict、closure gate | 已覆盖 |
| P1.1 假设与依赖 | Story、Detail Design、Discovery Ledger | 已覆盖 |
| P1.2 约束与范围边界 | 多个设计面与 scope gate | 已覆盖 |
| P1.3 需求/任务依赖风险追溯 | TASKS dependency 与 Trajectory，但不是每条需求都有 | 部分覆盖 |

| P2.1 功能/用户需求覆盖 | US/AC/TP/TC 链与 cardinality gate | 已覆盖 |
| P2.2 异常行为与范围 | Edge/Misuse/Fault、Error Design、exclusions | 已覆盖 |
| P2.3 技术/运行/质量约束 | Architecture、Detail 与 Quality Design surfaces | 已覆盖 |
| P2.4 依赖与交付计划 | TASKS checklist、orientation、commit plan | 已覆盖 |

| I1.3 模板声明与执行 | Template provenance 与 review gates | 已覆盖 |
| I2.1 标准术语与定义 | 局部字典存在，但缺少项目级统一语言 | 缺口 |
| I2.2 统一 ID 与记号 | 类别内较强，但跨制品类型仍不统一 | 部分覆盖 |
| I2.3 跨制品对齐与追溯 | Review gates 与 TestEvidenceChain | 已覆盖 |
| I2.4 一致组织结构 | 通用模板存在，但 Story 可选制品差异较大 | 部分覆盖 |
| I3.1 结构化组织 | 强 | 已覆盖 |
| I3.2 跨文档上下文与导航 | 有相关文档链接，但无完整制品集合地图 | 部分覆盖 |

| C1.1 行为产品规范 | Story、AC、Usage Guide | 已覆盖 |
| C1.2 产品/项目关注分离 | Work orientation 与制品分层 | 已覆盖 |
| C1.3 可追溯过渡到实现 | Lifecycle、TASKS、source links | 已覆盖 |

| C2.2 计划与任务组织 | `SPEC_makePlan`、TASK 模板、Trajectory | 已覆盖 |
| C2.3 需求到实现追溯 | TestEvidenceChain 与 review gates | 已覆盖 |
| C2.4 数据模型与演进 | Dictionary、State、Compatibility；演进计划是条件性的 | 部分覆盖 |

### 6.1 审计结论

CaTDD 对 EPIC 的大多数实践已有实质覆盖。缺口集中在五类问题：

1. 项目级术语与规范语气。
2. 制品集合的导航与语义聚合。
3. “一个陈述一个义务”和“一个陈述一个架构事实”的强制执行。
4. 从需求、任务到证据的完整依赖与风险连接。
5. 数据与接口的显式演进计划。

因此，缺口不是“CaTDD 缺少需求质量”，而是：

> CaTDD 具有强局部质量控制，但尚无 EPIC 式的整体规范制品集合审计。

## 7. CaTDD 可以向 EPIC 学习什么

### 改进 1：增加基于 EPIC 的规范充分性门禁

**EPIC 洞见：** 模板填写完整不等于规范充分，质量必须在制品集合层面判断。

**CaTDD 动作（两阶段渐进充分性模型，零重复）：**

按 `WHAT/WHY`（UserStory）与 `HOW`（配对 TASKS 台账）的职责边界，把 EPIC 规范充分性门禁分为两个递进阶段：

1. **第一阶段 —— 开启前故事级充分性（位于 `todoUS/*-UserStory.md` 的 `## Story Readiness Snapshot`）**：
   - 在 `SPEC_analyzeIssue`、`SPEC_analyzeFeature` 与 `SPEC_analyzeAbortedUserStory` 结束时执行（见 `SpecTodoUserStoryTemplate.md`）。
   - 将故事就绪检查映射到故事级 EPIC 维度（`E1 Unambiguous`、`E2 Singular`、`E3 Verifiable`、`P1 Dependency Control`、`P2 Complete`、`I1 Conforming`、`C1 Scope Discipline`），在故事进入 `SPEC_openUserStory` 之前拦截源头缺口。
2. **第二阶段 —— 制品集合级充分性（位于 `doingUS/*-UserStory-Tasks.md` 的 `## EPIC Specification Sufficiency`）**：
   - 在 `SPEC_makePlan` 创建配对任务文件时初始化完整 10 维表（见 `SpecDoingUserStoryTasksTemplate.md`），此时完整 EPIC 三元组（`Spec + Plan + Tasks`）首次同时具备，并且能覆盖经由 `SPEC_importUserStory` 直接入队的故事。
   - 在每次 `SPEC_review*` 门禁（`SPEC_reviewUserStory`、`SPEC_reviewArchDesign`、`SPEC_reviewDetailDesign`、`SPEC_reviewImplTests`、`SPEC_reviewProductCodes`）后由 `SPEC_updateMadePlan` 渐进刷新，并在 `SPEC_closeUserStory` 关闭前校验不存在未解决的阻断性 `gap` 或 `question`：

| EPIC 类别 | 维度 | 结论（Disposition） | 证据 / 受影响 ID | Owner / 下一步 |
| --- | --- | --- | --- | --- |
| Expressive (E) | `E1 Unambiguous` | `satisfied / partial / gap / question / N/A` | ... | ... |
| Expressive (E) | `E2 Singular` | ... | ... | ... |
| Expressive (E) | `E3 Verifiable` | ... | ... | ... |
| Precise (P) | `P1 Dependency Control` | ... | ... | ... |
| Precise (P) | `P2 Complete` | ... | ... | ... |
| Interpretable (I) | `I1 Conforming` | ... | ... | ... |
| Interpretable (I) | `I2 Consistent` | ... | ... | ... |
| Interpretable (I) | `I3 Comprehensible` | ... | ... | ... |
| Compartmentalized (C) | `C1 Scope Discipline` | ... | ... | ... |
| Compartmentalized (C) | `C2 Implementation Planning` | ... | ... | ... |

不必为每个项目强制计算数值总分。disposition 和证据通常比脆弱的总分更有用。

### 改进 2：增加规范语气与统一语言门禁

**EPIC 洞见：** `should`、`may`、`must`、`must not` 会产生不同执行含义；跨制品术语漂移会造成错误等价。

**CaTDD 动作（以架构层 `README_UbiLang.md` 为唯一语义真理源，`projectContext.md` 零重复）：**

- 将项目根目录的 `README_UbiLang.md`（由 `slashCommands/templates/README_UbiLangTemplate.md` 初始化）归入**架构导向（Architecture-Oriented）**SPEC 文档（由 `SPEC_takeArchDesign` / `SPEC_updateArchDesign` / `SPEC_reviewArchDesign` 管理），作为项目与限界上下文（Bounded Context）统一语言（`EPIC E1.3 & I2.1`）及受控规范语气词汇（`EPIC E1.4`）的唯一权威归属。
- 为保护 `.catdd/spec/projectContext.md` 的 200 行工作记忆预算，`projectContext.md` 仅保留指向 `README_UbiLang.md` 的单行 `REFERENCE` 引用，绝不重复拷贝术语表。
- 要求 `SPEC_takeArchDesign`、`SPEC_updateArchDesign` 与 `SPEC_updateUserStory` 将新增或变更的领域术语同步到 `README_UbiLang.md`，详细设计（`SPEC_takeDetailDesign`）只消费该术语契约而不重定义。
- 在 UserStory 的 `THEN` 验收结果、业务规则、`README*` 设计不变量（$K$）、测试 `@[Expect]` 预期以及 `slashCommands/` 与 `methodPrompts/` 契约中使用受控情态词：
  - `MUST`（`必须` / `SHALL`）：强制性硬义务，必须映射到 TP/TC，未验证即阻断门禁。
  - `MUST NOT`（`严禁` / `绝不` / `SHALL NOT`）：禁止行为或安全边界。
  - `SHOULD` / `SHOULD NOT`（`应当` / `不应`）：预期采用，除非有记录在案的权衡、ADR 或例外条件。
  - `MAY`（`可以` / `可选`）：允许但非必需的可选行为。
- 在歧义坏味道分类器（`CaTDD_methodPrompt-testPointDiscovery.md`）中增加 `SMELL-MODAL`，并在 `SPEC_reviewUserStory`、`SPEC_reviewArchDesign`、`SPEC_reviewDetailDesign` 中检查弱情态词（无例外条件的 `"should"` / `"might"`）及相对 `README_UbiLang.md` 的同义词漂移。
- 无论制品使用哪种自然语言，都保留机器可读 ID 和模板结构，不能只依赖英文关键词扫描。

这不是削弱 `ONE-MORE-THING`，而是让歧义在升级前先获得明确的术语和语气维度。

### 改进 3：把跨制品一致性升级为一等门禁

**EPIC 洞见：** 单独看都合格的文档之间仍可能相互矛盾。

**CaTDD 动作：**

为审查增加语义差异矩阵：

| 来源义务 | Story | Guide | Architecture | Detail Design | Discovery Ledger | US/AC/TC | Code/Evidence |
| --- | --- | --- | --- | --- | --- | --- | --- |
| R-01 | preserved | preserved | refined | ... | TP-01 | TC-03 | passing |

每次转换必须分类为：

- `PRESERVED`：含义未改变。
- `REFINED`：经过明确理由后收窄或分解。
- `REFERRED`：明确交给其他责任方。
- `EXCLUDED`：经批准明确排除。
- `DIVERGED`：发生冲突，必须返工。
- `UNKNOWN`：缺少证据，必须提问。

这是 CaTDD 现有 TP/TC 追溯的上游补充。

### 改进 4：把 EPIC 实践分为核心、风险触发与建议级

**EPIC 洞见：** 实践评价随上下文变化，论文支持增量采用，而不是普遍等权仪式。

**CaTDD 动作：**

建立三级适用性：

| 层级 | 应用方式 |
| --- | --- |
| Core（核心） | 对非平凡 Story 始终应用：澄清、可测量结果、范围、验证、稳定 ID、跨制品一致 |
| Risk-triggered（风险触发） | 涉及安全、并发、迁移、硬件、外部依赖、分布式状态或不可逆接口时增加 |
| Advisory（建议） | 文档、导航、理解辅助等实践，一般不阻塞简单可逆变更 |

阻塞强度应服从风险。一个纯文档小改动不应与安全关键迁移承担相同的制品仪式。

### 改进 5：记录规范质量债务

**EPIC 洞见：** 维度可以部分满足或明确不适用，不能让所有状态都坍缩为通过/失败。

**CaTDD 动作：**

在实现缺口之外维护 EPIC 债务：

```text
EPIC-01 | E1.4 | partial | AC 中 should/must 使用不一致
        | owner=product | resolve-before=implementation | status=open

EPIC-02 | I2.1 | gap | "session" 与 "conversation" 含义不一致
        | owner=architecture | resolve-before=design_approval | status=open
```

债务不必在每个阶段都自动阻塞，但必须包含：

- 严重度。
- 受影响义务。
- 最迟解决阶段。
- 责任人。
- 关闭证据。

这样既让质量权衡可见，又不会把 EPIC 变成 40 个无条件复选框。

### 改进 6：把完成条件写入规范，而不只放在流程中

**EPIC 洞见：** 验证完整性和就绪性必须成为规范内容的一部分。

**CaTDD 动作：**

对每个重要 Story 或质量义务记录：

- 必需证据。
- 必需环境。
- 必需测试层级。
- 必需审查门禁。
- 哪些情况表示“尚未完成”。
- 哪些内容可以延后，且不改变当前验收声明。

CaTDD 已有 `ready_for_implementation` 和 review verdict。进一步改进是让完成定义 针对具体 Story，而不是完全依赖通用 Flow checklist。

## 8. 超越 EPIC：对 CaTDD 的深层启示

### 8.1 可测试是必要条件，但不是充分条件

这是整个比较中最重要的结论。

CaTDD 当前要求每个 AC 都能转换为可测试义务。这能阻止模糊标准进入测试实现， 但不能证明 AC 集合完整、范围正确、术语一致，或与 Plan 一致。

因此：

> CaTDD 必须同时门禁可执行充分性与规范充分性。

Story 不能仅因为“这个 AC 有 TC”就进入下一阶段，还必须证明制品集合保留了相关意图。

### 8.2 规范质量是跨转换守恒属性

EPIC 给出一组质量维度。更深一层的操作化表述是：每条义务在转换过程中都必须 被保留：

```text
业务意图
  -> Story
  -> AC
  -> Design Constraint
  -> Test Point
  -> Test Case
  -> Code Behavior
  -> Runtime Evidence
```

在每一层，义务可以被保留、细化、拆分、转交或明确排除，但不能静默消失或改变含义。

可称之为**转换保持属性（Transformation Preservation Property）**：

> 对每条关键义务而言，从来源意图到可执行证据的转换，要么保持含义，要么记录 一个可见且经批准的含义变化。

这是偏静态 rubric 的 EPIC 尚未完全解决的动态维度。CaTDD 的 TestEvidenceChain 已在下游近似实现它；若向上游扩展，就能形成完整制品集合不变量。

### 8.3 规范债务先于测试债务，并可能掩盖测试债务

CaTDD 已经暴露 `GAP`、`QUESTION`、`EXCLUDED` 和未链接测试点。EPIC 表明， 规范债务可能在这些状态出现之前就已经存在。

例子：

- 每个 AC 都有 TC，但两个 AC 用不同措辞描述同一义务。
- 每个场景都可测试，但 Non-goals 漏掉 Plan 已静默支持的平台。
- Detail Design 声明接口，但 Story 从未定义其生命周期所有权。
- Plan Task 已完成，却实现了规范从未论证过的技术选择。

这些不是测试失败，而是**测试前规范债务**。CaTDD 需要在不误标 TP GAP、也不把 所有问题都视为产品阻塞的前提下记录它们。

### 8.4 EPIC 评估声明充分性，CaTDD 仍须评估工程合理性

一份制品可以表达充分，却仍然描述错误架构、不安全策略或错误产品决定。EPIC 并不证明所声明意图是否明智。

CaTDD 必须继续保持不同透镜：

- **规范充分性**：意图是否清晰且自洽？
- **架构有效性**：选择的结构是否合适？
- **实现质量**：代码是否安全满足义务？
- **运行证据**：部署系统是否真的按声明工作？

高 EPIC 分数不是架构批准。

### 8.5 规范本身也需要 Fitness Function

此前架构分析建议采用可执行治理。EPIC 提供了可机械或半机械检查的属性：

- 每个引用的 ID 都能解析。
- 每个 Story 范围项都在下游义务或显式排除中出现。
- 每个关键 AC 都有验证方法和完成条件。
- 每个质量场景都有阈值或精确谓词。
- 每个规范语气词都属于受控词汇。
- 每个需求变化都有明确的 delta 分类。
- 每个 `SUPERSEDED` 决策或撤回需求仍然可发现。
- 每个 `QUESTION` 都有 owner 和最迟可解决阶段。

这会把 EPIC 从事后 rubric 变成**规范 fitness function**。它比静态评分更有价值， 因为能在制品变化时持续检测漂移。

### 8.6 歧义应按解决路径分类

`ONE-MORE-THING` 是很强的安全不变量，但执行层需要知道停止的原因。EPIC 对 未决标记和已决需求的区分，可以引出更细的分类：

| 歧义类型 | 正确动作 |
| --- | --- |
| 来源可解决 | 读取权威制品后继续，无需提问 |
| 政策可解决 | 升级给决策 owner，不得自行推断 |
| 范围可解决 | 经批准记录显式排除或转交 |
| 执行可解决 | 记录验证限制，不改变意图 |
| 不可消除的歧义 | 通过 `ONE-MORE-THING` 停止 |

这保留 CaTDD 禁止猜测的规则，同时避免权威来源已经解决时产生无谓问题。

### 8.7 EPIC 是质量罗盘，不是参与奖杯

论文报告多数实践都获得多数实践者认可，但评分并不均匀。低分说明真实权衡：

- 早期详细交付计划可能过早。
- 过度追溯会产生阅读成本。
- 某些智能体能在上下文中自行解决部分缺口。
- 不同实践会随项目成长而提高价值。

因此 CaTDD 应优化**单位规范投入产生的正确性**，而不是追求 EPIC 覆盖率最大化。

真正的问题不是：

> 是否满足了全部 40 项实践？

而是：

> 本 Story 的关键风险中，哪些已经受到显式、一致、可验证意图的保护，哪些仍只是假设？

### 8.8 EPIC 补全了测试先行的“Why”

TDD 解释了如何把已知义务变成可执行检查。EPIC 解释了为什么义务本身仍可能不充分。

组合关系是：

```text
EPIC：让意图足够明确且自洽
CaTDD：让意图可测试并具备证据
RED/GREEN：证明实现对可执行意图的满足
Review Gates：防止无证据进入下一生命周期阶段
```

这比单独使用任一框架更强：EPIC 保护规范含义，CaTDD 保护执行完整性。

## 9. 建议的 CaTDD 控制模型

以下模型把 EPIC 集成进 CaTDD，而不复制已有方法。

### 9.1 门禁位置

| 生命周期位置 | EPIC 贡献 | CaTDD 责任命令 |
| --- | --- | --- |
| 意图澄清 | 无歧义、范围、产品/实现分离 | `SPEC_clearStoryIntent` |
| 需求审查 | E/P/I 维度、术语、完成条件 | `SPEC_reviewUserStory` |
| 架构审查 | 跨制品一致、约束、依赖 | `SPEC_reviewArchDesign` |
| 详细设计审查 | 技术上下文、数据模型、追溯、可测试性 | `SPEC_reviewDetailDesign` |
| 测试设计 | 验证场景、方法、完成证据 | `SPEC_designTests` / Discovery Gate |
| 实现审查 | 需求到代码的追溯与漂移 | `SPEC_reviewProductCodes` |
| 关闭 | 完整制品集合充分性与未解决债务 | `SPEC_closeUserStory` |

### 9.2 门禁公式

不要用聚合 EPIC 分数取代现有 verdict。使用复合就绪谓词：

```text
ready =
  没有未解决的阻塞性 QUESTION
  AND 没有未处置的范围内 GAP
  AND 必需 EPIC 维度已满足或已被显式风险接受
  AND 声明范围内 TestEvidenceChain 完整
  AND 必需 review gates 均为 PASS
```

EPIC 部分是证据，不凌驾于 CaTDD 的安全规则之上。

### 9.3 三级采用方案

#### Tier A：核心门禁

优先实施：

- 主动澄清。
- 可测量结果。
- 显式范围和验证边界。
- 稳定 ID。
- 跨制品一致。
- 需求到实现追溯。
- 可测试的完成条件。

这些对应最高风险失效模式，CaTDD 也已有较强支撑。

#### Tier B：风险触发门禁

以下情况必须增加：

- 安全或隐私。
- 外部依赖或分布式状态。
- 并发或生命周期状态转换。
- 数据迁移或兼容性。
- 硬件或运行约束。
- 不可逆架构边界。

增加检查：

- 依赖验证与失败模式处理。
- 技术/运行约束。
- 数据与接口演进。
- 跨文档导航与实现计划。

#### Tier C：建议性质量改进

适用于：

- 每个次级陈述的原子措辞。
- 所有制品类型的统一记号。
- 文档组织高度一致。
- 更多理解辅助示例。

当这些问题不威胁当前验收时，记录为改进债务即可。

## 10. 可执行演进路线

### 阶段 1：建立质量透镜

1. 在 Story 或 TASKS 中增加 `EPIC Specification Sufficiency` ledger。
2. 在 `projectContext.md` 或独立 glossary 中增加受控术语和规范语气指导。
3. 定义转换 disposition：`PRESERVED`、`REFINED`、`REFERRED`、`EXCLUDED`、 `DIVERGED`、`UNKNOWN`。
4. 在审查门禁中加入制品集合追溯矩阵。

### 阶段 2：强化门禁

1. 扩展 `SPEC_reviewUserStory`，加入 E/P/C 充分性检查。
2. 扩展 `SPEC_reviewDetailDesign`，加入跨制品一致性和数据/接口演进检查。
3. 扩展 `SPEC_closeUserStory`，确认规范债务已关闭、接受或正确转交。
4. 更新审查示例，覆盖：
   - 可测试但范围过大的 AC。
   - 表面一致但语义漂移的制品。
   - Plan 实现未经批准的 Design Choice。
   - 实现正确但术语歧义仍未解决。

### 阶段 3：增加 Fitness Functions

优先以确定性脚本或审查断言实现：

- 所有引用 ID 均可解析。
- 检测重复或孤立需求 ID。
- 检测缺少验证方法和完成谓词的需求。
- 检测从未进入下游义务或显式排除的范围项。
- 上游需求变化后，检测下游证据是否过期。
- 标记模糊情态词和术语漂移。
- 验证每个高风险义务都有 fitness function 或证据 owner。

### 阶段 4：验证，而不是假定

在把 EPIC 检查变成普遍阻塞项前：

1. 对多种 Story 类型试点：小型 CLI 改动、架构改动、并发/有状态改动、 纯质量改动和安全敏感改动。
2. 测量审查重工、错误阻塞、漏掉的歧义和制品阅读成本。
3. 比较启用与不启用 EPIC 门禁时的 CaTDD 输出。
4. 保留哪些实践真正防止缺陷或重工的证据。

这也符合 EPIC 自身的经验：在实践中评估实践，而不是只依据理论吸引力。

## 11. 风险与反模式

### 11.1 把 EPIC 变成 40 个强制复选框

这会产生文档数量，而不一定按比例降低风险。应使用分级采用与显式不适用。

### 11.2 把 EPIC 分数当作真理

聚合分数会隐藏具体失败维度及其严重性。优先使用 ID、证据、disposition 和 owner， 而不是单一数字。

### 11.3 用实现决策覆盖产品意图

当技术约束确实属于必需行为时，它可以合法出现在规范中。判断标准不是“不能有技术 内容”，而是产品需求是否仍可识别并保持可追溯。

### 11.4 把文档质量汇报成运行质量

规范充分性不证明实现正确、安全、高性能或部署成功。必须保持证据类别分离。

### 11.5 用 EPIC 绕过 `ONE-MORE-THING`

Rubric 不能授权一个假设。未解决的政策决定仍然是人类决定，除非权威来源已经明确 解决它。

### 11.6 把测试措辞机械复制为规范

如果 AC、TP 和测试名都机械复制自不完整来源，所有制品可以高度一致，却共同保留 同一个遗漏。EPIC 的单一性和可理解性检查应鼓励独立审查，而不是短语复制。

## 12. 综合结论：CaTDD 是 EPIC 周围的执行系统

| 维度 | EPIC | CaTDD |
| --- | --- | --- |
| 核心问题 | 制品集合是否足够清晰，可安全实现？ | 意图是否被转换为可追溯、可执行证据？ |
| 核心价值 | 制品集合质量词汇与实证基础 | 测试先行执行、分类与生命周期强制执行 |
| 相对优势 | 上游完整性、规范语气、跨制品质量 | 测试设计深度、语义 RED、运行证据、有界智能体流程 |
| 主要限制 | 没有可执行控制闭环，分数不证明正确性 | 强局部门禁不能独立证明整体规范充分性 |
| 最佳集成点 | 执行前充分性证据 | 门禁消费、返工路由与证据保存 |

最稳妥的结论是：

> EPIC 为 CaTDD 的验证层增加了其上方缺失的评估层。

CaTDD 已以操作化形式实现多数 EPIC 实践。真正高价值的演进，是显式表达这些实践 之间的制品集合关系，统一规范术语与语气，并把规范质量作为持续变化的动态属性， 而不是一次性文档审查。

最终方法论不应是“EPIC vs. CaTDD”，而应是：

```text
EPIC 规范充分性
  -> CaTDD 测试点发现
  -> 注释鲜活的 US/AC/TC 设计
  -> 语义 RED/GREEN 实现
  -> 运行与审查证据
  -> 带显式残余风险的关闭
```

这种组合保留了 EPIC 最重要的洞见——智能体不应替规范决定它没有说出的内容—— 同时保留了 CaTDD 最重要的保证：在没有验证已声明义务的证据之前，实现不得推进。
