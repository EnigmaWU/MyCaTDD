# 2610.07534 (EPIC) vs. CaTDD: Comparative Analysis & Evolution Roadmap

This document compares the EPIC framework for spec-driven development (SDD) by
Bruno Claudino, Ruizhe Xing, Yuanhao Zuo, Tyler Menezes, Anita Sarma, Kostadin
Damevski, and Zixuan Feng, published as arXiv:2610.07534, with CaTDD's current
operational methodology and SpecFlow implementation. It follows the
comparative-analysis pattern established by
[2607.16680_vs_CaTDD.md](2607.16680_vs_CaTDD.md), then goes beyond the surface
mapping to examine where EPIC changes the way CaTDD should reason about
specification quality.

Sources:

- [EPIC paper](<2610.07534（The EPIC Framework for Spec-Driven Development).pdf>)
- [Existing SGRM comparison](2607.16680_vs_CaTDD.md)
- Current `methodPrompts/`, `slashCommands/`, and README SPEC templates in this repository

## 1. Executive Summary

EPIC and CaTDD address the same failure mode from different positions in the
development lifecycle.

EPIC asks:

> Is the set of specification, plan, and task artifacts sufficiently clear,
> complete, consistent, and verifiable for an implementation agent to act without
> silently inventing missing intent?

CaTDD asks:

> Has source-backed intent been converted into a traceable, testable, executable
> obligation, and has implementation advanced only through evidence-bearing
> RED/GREEN and review gates?

They are complementary:

- EPIC is primarily an **artifact-quality lens and evaluation framework**.
- CaTDD is primarily an **execution methodology, verification language, and
  lifecycle control system**.
- EPIC measures whether intent has been made sufficiently explicit.
- CaTDD controls whether explicit intent has been designed, tested, implemented,
  reviewed, and closed.

The strongest conclusion is not that CaTDD needs forty new checkboxes. It is that
CaTDD needs one additional object of governance:

> The quality of the specification artifact set must be judged before testability
> is accepted as sufficient evidence of readiness.

A testable AC can still be an incomplete AC. A consistent plan can still implement
the wrong scope. A passing test can still validate an obligation that was never
properly stated. TDD guarantees discipline relative to expressed intent; it does
not independently guarantee that the expressed intent is sufficient.

This suggests three high-value additions to CaTDD:

1. **Artifact-set sufficiency gate**: review the story, guide, architecture, detail
   design, verification design, plan, and tasks as one semantic set rather than as
   independently passing documents.
2. **Ubiquitous-language and normative-language controls**: standardize terms,
   identifiers, `MUST`/`MAY`/`MUST NOT` intent, scope boundaries, and completion
   predicates before downstream artifacts interpret them differently.
3. **EPIC quality debt and risk tiering**: record partial or missing specification
   practices as explicit, owned debt rather than treating every practice as either
   satisfied or blocking.

CaTDD is already stronger than EPIC in executable design, test-point discovery,
semantic RED validation, runtime evidence ownership, and bounded lifecycle
governance. EPIC should therefore be adopted as a **pre-execution quality lens**,
not as a replacement for CaTDD's test-driven operating model.

## 2. What EPIC Actually Contributes

### 2.1 The Unit of Quality Changes

EPIC's central theoretical contribution is the shift from single-requirement quality
to artifact-set quality.

Traditional requirements engineering asks whether a requirement is unambiguous,
singular, and verifiable. EPIC retains those expectations but adds:

- Dependencies and constraints that condition implementation.
- Separation of required behavior from design and implementation decisions.
- Explicit planning and task information.
- Agreement among specification, plan, and tasks.

The paper's ten dimensions are:

| EPIC category | Dimensions | Governing question |
| --- | --- | --- |
| Expressive | Unambiguous, Singular, Verifiable | What must the system do, and how do we know it is done? |
| Precise | Dependency Control, Complete | Under what assumptions and scope must it do so? |
| Interpretable | Conforming, Consistent, Comprehensible | Can humans and agents interpret the artifact set the same way? |
| Compartmentalized | Scope Discipline, Planning | Are product scope and implementation guidance separated and traceable? |

### 2.2 EPIC's Forty Practices

EPIC operationalizes the ten dimensions through forty practices.

#### Expressive

- E1 Unambiguous
  - E1.1 Explicit clarification-seeking.
  - E1.2 Quantified or measurable requirements.
  - E1.3 Bounded vocabulary and enumerated definitions.
  - E1.4 Normative and structural consistency.
  - E1.5 Explicit scope and verification boundaries.
- E2 Singular
  - E2.1 Atomic functional and behavioral statements.
  - E2.2 Singular architecture and design facts.
  - E2.3 Isolated risk, assumption, edge-case, and constraint entries.
  - E2.4 Singular definitional, scenario, and relational statements.
  - E2.5 Singular security and privacy properties.
- E3 Verifiable
  - E3.1 Verification criteria and measurable outcomes.
  - E3.2 Verification scenarios and validation methods.
  - E3.3 Comprehensive verification coverage.
  - E3.4 Verification completion and readiness.

#### Precise

- P1 Dependency Control
  - P1.1 Declared assumptions and dependencies.
  - P1.2 Explicit constraint and scope boundaries.
  - P1.3 Requirement- and task-level dependency and risk traceability.
  - P1.4 Dependency verification and failure-mode handling.
- P2 Complete
  - P2.1 Functional and user-requirement coverage.
  - P2.2 Exceptional behavior and scope definition.
  - P2.3 Technical, operational, and quality constraints.
  - P2.4 Dependency and delivery planning.
  - P2.5 Specification completeness management.

#### Interpretable

- I1 Conforming
  - I1.1 Standardized document structure.
  - I1.2 Stable, unique requirement identifiers.
  - I1.3 Explicit template declaration and enforcement.
- I2 Consistent
  - I2.1 Standardized terminology and concept definitions.
  - I2.2 Uniform identifiers and notation.
  - I2.3 Cross-artifact alignment and traceability.
  - I2.4 Consistent organizational structure.
- I3 Comprehensible
  - I3.1 Structured document organization.
  - I3.2 Cross-document context and navigation.
  - I3.3 Comprehension support.

#### Compartmentalized

- C1 Scope Discipline
  - C1.1 Behavioral product specification.
  - C1.2 Separation of product and project concerns.
  - C1.3 Traceable transition to implementation.
- C2 Implementation-Planning Information
  - C2.1 Technical context and implementation foundations.
  - C2.2 Implementation planning and task organization.
  - C2.3 Requirements-to-implementation traceability.
  - C2.4 Implementation data models and evolution planning.

### 2.3 Empirical Basis and Limits

The EPIC study is substantially broader than a design essay:

- 850 candidate repositories were discovered.
- 206 repositories were screened.
- 114 repositories using AI-agent-oriented specification artifacts were analyzed.
- Forty practices were derived from 5,675 coded artifact segments.
- Thirty grey-literature sources were cross-checked.
- Fifteen experienced SDD practitioners evaluated the practices.
- SonarQube results covered 100 repositories and GitHub activity covered 109.

The paper reports several associations between specification quality and repository
outcomes:

- Top-band repositories had 11.8% bug-fix commits versus 20.4% in the bottom band.
- Median cyclomatic complexity per KLOC was 15.4% lower in the top band.
- Median vulnerability density was roughly half in the top band, although the
  full-range correlation was not significant.
- Median contributors were 12.5 versus 3.
- Pull requests, merged pull requests, issues, and commits were also higher in
  the top band.

These results justify taking EPIC seriously. They do not establish causation.
Repository maturity, team size, language, project type, existing contribution
activity, and documentation investment remain plausible confounders. The paper
explicitly describes the outcome results as exploratory and observational.

The practical consequence is:

> EPIC supplies a well-grounded diagnostic vocabulary, not a proven universal
> compliance standard.

## 3. Structural Taxonomy: EPIC vs. CaTDD

```text
┌──────────────────────────────────────────────────────────────┐
│ EPIC                                                         │
├──────────────────────────────────────────────────────────────┤
│ Specification + Plan + Tasks                                 │
│ E: Expressive   -> meaning, singularity, verification        │
│ P: Precise      -> dependencies, completeness, constraints   │
│ I: Interpretable-> conventions, consistency, comprehension   │
│ C: Compartment. -> product intent vs implementation planning │
│                                                              │
│ 0-3 dimension scores; 40 practices; evidence from artifacts  │
└───────────────────────────┬──────────────────────────────────┘
                            │ complementary quality lens
                            ▼
┌──────────────────────────────────────────────────────────────┐
│ CaTDD and Px-SpecFlow                                        │
├──────────────────────────────────────────────────────────────┤
│ Story intent -> README SPEC docs -> detailed design          │
│ -> discovery ledger -> US/AC/TP/TC -> RED/GREEN              │
│ -> reviews -> commit -> closure                             │
│                                                              │
│ F: Contract      -> P0 Typical / Edge / Misuse / Fault       │
│ Model: P1        -> State / Capability / Interaction / Race  │
│ Envelope: P2     -> Quality operating constraints             │
│ Learning: P3     -> Demo and onboarding evidence              │
│                                                              │
│ TestEvidenceChain; runtime evidence; deterministic gates      │
└──────────────────────────────────────────────────────────────┘
```

EPIC's categories map approximately to CaTDD's lifecycle as follows:

| EPIC concern | Primary CaTDD location | Current strength |
| --- | --- | --- |
| Expressive requirements | Story, AC ledger, requirement review | Strong; singular and normative wording are still partial |
| Dependency and completeness | Scope, risks, assumptions, design surfaces, discovery ledger | Strong |
| Interpretability | IDs, templates, trace links, review gates | Strong structurally; terminology registry is weaker |
| Product/implementation separation | Flow orientation, story vs design vs tasks | Strong |
| Verification and completion | Discovery Gate, review contracts, RED/GREEN, closure | Stronger than EPIC's audit-only model |

The deeper relationship is not "EPIC replaces missing CaTDD practices." It is:

- EPIC provides the **quality predicate for the upstream artifact set**.
- CaTDD provides the **executable control system that consumes that predicate**.

## 4. SAME Analysis: Where EPIC and CaTDD Converge

### 4.1 Rejecting Silent Agent Assumptions

Both frameworks begin from the same observation: an agent may fill silence with a
plausible but unauthorized decision.

CaTDD's universal `ONE-MORE-THING` rule and its `QUESTION` ledger prevent an
unresolved source, oracle, scope, or ownership decision from being silently
converted into behavior. EPIC's explicit clarification-seeking practice and its
unresolved-decision markers express the same invariant at the specification layer.

The shared principle is:

> Silence is not a specification decision.

### 4.2 Measurable or Observable Completion

EPIC requires verification criteria, methods, coverage, and completion conditions.
CaTDD requires source-backed oracles, verification methods, category coverage, and
readiness gates. The terminology differs, but both reject "done" as an assertion
made by the implementation agent.

CaTDD goes further by distinguishing:

- AC as caller/user value.
- TP as a defensive technical obligation.
- TC as an executable verification artifact.
- RED as semantic failure for the intended reason.
- GREEN as a passing executable obligation.
- `ready_for_implementation` as distinct from release readiness.

### 4.3 Traceability by Construction

EPIC recommends stable IDs and cross-artifact traceability. CaTDD already defines
the `TestEvidenceChain`:

```text
Source -> Rule / Invariant -> TP -> Oracle -> Category
       -> US / AC / TC -> RED / GREEN evidence
```

CaTDD is stronger here because it traces not only documentation elements but also
the defensive test rationale and executable verification evidence.

### 4.4 Explicit Scope and Exceptional Behavior

EPIC's scope exclusions, exceptional behavior, and technical/operational
constraints overlap CaTDD's:

- Story `Scope` and `Non-goals`.
- `Typical`, `Edge`, `Misuse`, and `Fault` classification.
- `REFERRED` versus `EXCLUDED` discovery dispositions.
- Error, resource, compatibility, security, and diagnostic design surfaces.

Both frameworks recognize that an undefined boundary is not the same as an
intentional exclusion.

### 4.5 Human Escalation Instead of Lowering the Bar

EPIC recommends unresolved clarification rather than allowing the generator to
invent policy. CaTDD's bounded rework, `ONE-MORE-THING`, review verdicts, and
human escalation implement the same safety posture operationally.

### 4.6 Separating Product Intent from Implementation Guidance

EPIC's Compartmentalized category separates behavioral product requirements from
technical plans and task information. CaTDD's flow already distinguishes:

- Intent clearing.
- Requirement-oriented work.
- Design-oriented work.
- Implementation-oriented work.

The task artifact and TestEvidenceChain then reconnect those layers without
collapsing them.

## 5. DIFF Analysis: Where the Frameworks Are Complementary

| Dimension | EPIC | CaTDD |
| --- | --- | --- |
| Primary artifact | Specification, plan, tasks | Story, SPEC docs, ledger, test designs, tests, code |
| Primary purpose | Judge artifact quality | Control design-to-code execution |
| Unit of analysis | Artifact set | Source-to-evidence chain |
| Evaluation style | Ten 0-3 dimensions and forty practices | Focused gates, verdicts, dispositions, and test evidence |
| Requirement perspective | Primarily user/system obligations | AC value perspective plus TP defensive perspective |
| Quality of omission | Rubric evidence and applicability | `QUESTION`, `EXCLUDED`, `REFERRED`, `GAP`, `BLOCKED` |
| Product/implementation split | Spec versus plan/tasks | Intent, requirement, design, test, implementation phases |
| Completion evidence | Criteria and completion conditions | Semantic RED/GREEN, review gates, runtime evidence |
| Agent safety | Clarification markers and incomplete-spec detection | Universal human-escalation invariant and Loop Guard |
| Strength | Breadth, comparability, empirical grounding | Executability, testability, trace depth, lifecycle control |
| Main risk | Documentation-heavy; observational evidence | Local gates can miss upstream semantic insufficiency |

### 5.1 Quality Lens vs. Control Loop

EPIC is a lens. It tells developers what to inspect and how to score it.

CaTDD is a control loop. It tells developers and agents what may happen next,
what evidence is required, and when the process must stop.

The combination is useful:

```text
EPIC quality evidence -> CaTDD gate decision -> bounded rework or escalation
```

A dimension score without a gate changes nothing operationally. A gate without a
dimension vocabulary may miss why it should have failed.

### 5.2 External Artifact Set vs. Comment-Alive Execution Model

EPIC treats specification, plan, and tasks as a document pipeline. CaTDD places
some design intent directly in test comments and keeps discovery ledgers near the
verification evidence.

That difference is not a conflict:

- EPIC evaluates upstream documents before implementation.
- CaTDD preserves executable design intent after implementation begins.
- CaTDD's in-situ comments reduce context distance.
- EPIC's artifact-set view exposes cross-document omissions that in-situ comments
  cannot detect by themselves.

### 5.3 Requirements Quality vs. Test Adequacy

EPIC does not design tests. It asks whether requirements and plans are sufficiently
clear to be acted upon.

CaTDD does not presently score the holistic quality of the artifact set. It asks
whether ACs can become test points and TCs and whether design sources support
those obligations.

A test suite can be internally rigorous while collectively testing a poorly
scoped artifact set. This is the most important gap.

### 5.4 A Rubric vs. An Engineering Method

EPIC is relatively tool-neutral and can be applied to a flat requirements document,
GitHub Spec Kit, OpenSpec, or another SDD pipeline. CaTDD is opinionated about
lifecycle, categories, test structure, traceability, and evidence.

EPIC can therefore supply vocabulary to CaTDD, while CaTDD can supply enforcement
and domain-specific rigor to EPIC.

### 6.1 Interpretation of the Audit

CaTDD covers most of EPIC substantially. The gaps cluster into five concerns:

1. Project-wide terminology and normative language.
2. Artifact-set navigation and semantic aggregation.
3. Enforcement of one-obligation-per-statement and architecture-fact singularity.
4. Complete dependency/risk linkage from requirement through task and evidence.
5. Explicit specification-evolution planning for data and interfaces.

The gap is therefore not "CaTDD lacks requirements quality." It is:

> CaTDD has strong local quality controls but no equivalent of EPIC's holistic
> artifact-set audit.

## 7. What CaTDD May Learn from EPIC

### Refinement 1: Add an EPIC-Based Specification Sufficiency Gate

**EPIC insight:** Template completion is not specification sufficiency. Quality is
judged across the artifact set.

**CaTDD action (Two-Stage Progressive Sufficiency, zero duplication):**

Split the EPIC sufficiency check across the two natural SpecFlow artifacts so
`WHAT/WHY` (UserStory) and `HOW` ( paired TASKS ledger) stay cleanly separated:

1. **Stage 1 — Pre-Open Story Sufficiency in `todoUS/*-UserStory.md` (`## Story Readiness Snapshot`)**:
   - Evaluated at the end of `SPEC_analyzeIssue`, `SPEC_analyzeFeature`, and
     `SPEC_analyzeAbortedUserStory` (in `SpecTodoUserStoryTemplate.md`).
   - Maps the pre-open readiness lenses to the story-level EPIC dimensions
     (`E1 Unambiguous`, `E2 Singular`, `E3 Verifiable`, `P1 Dependency Control`,
     `P2 Complete`, `I1 Conforming`, `C1 Scope Discipline`) before a story can be
     marked `Ready` for `SPEC_openUserStory`.
2. **Stage 2 — Artifact-Set Sufficiency in `doingUS/*-UserStory-Tasks.md` (`## EPIC Specification Sufficiency`)**:
   - Seeded by `SPEC_makePlan` (in `SpecDoingUserStoryTasksTemplate.md`) once the
     full EPIC triad (`Spec + Plan + Tasks`) exists — catching both analyzed
     stories and stories imported directly via `SPEC_importUserStory`.
   - Progressively updated by `SPEC_updateMadePlan` after each `SPEC_review*`
     gate (`SPEC_reviewUserStory`, `SPEC_reviewArchDesign`,
     `SPEC_reviewDetailDesign`, `SPEC_reviewImplTests`,
     `SPEC_reviewProductCodes`), and verified before `SPEC_closeUserStory` so no
     unresolved blocking `gap` or `question` disposition remains:

| EPIC Category | Dimension | Disposition | Evidence / affected IDs | Owner / next action |
| --- | --- | --- | --- | --- |
| Expressive (E) | `E1 Unambiguous` | `satisfied / partial / gap / question / N/A` | ... | ... |
| Expressive (E) | `E2 Singular` | ... | ... | ... |
| Expressive (E) | `E3 Verifiable` | ... | ... | ... |
| Precise (P) | `P1 Dependency Control` | ... | ... | ... |
| Precise (P) | `P2 Complete` | ... | ... | ... |
| Interpretable (I) | `I1 Conforming` | ... | ... | ... |
| Interpretable (I) | `I2 Consistent` | ... | ... | ... |
| Interpretable (I) | `I3 Comprehensible` | ... | ... | ... |
| Compartmentalized (C) | `C1 Scope Discipline` | ... | ... | ... |
| Compartmentalized (C) | `C2 Implementation Planning` | ... | ... | ... |

Do not require a numeric score for every project. The disposition and evidence are
more useful than a brittle aggregate score.

### Refinement 2: Add a Normative and Ubiquitous Language Gate

**EPIC insight:** Small wording choices alter agent behavior. `should`, `may`,
`must`, and `must not` have different operational meanings, and inconsistent
terminology creates false equivalence across artifacts.

**CaTDD action:**

- Define a project glossary in `projectContext.md` or another shared language
  surface.
- Require each story to list newly introduced or changed terms.
- Use a controlled modal vocabulary:
  - `MUST`: mandatory obligation.
  - `MUST NOT`: prohibited behavior.
  - `MAY`: permitted but not required.
  - `SHOULD`: conditional preference requiring a recorded exception process.
- Add a review check for synonym drift, such as `tool`, `command`, `operation`,
  `handler`, and `adapter` referring inconsistently to the same boundary.
- Preserve machine-readable IDs and template structure in every language; do not
  rely only on English keyword scanning.

This refines rather than replaces `ONE-MORE-THING`: ambiguity is still escalated,
but terminology and modality become explicit review dimensions.

### Refinement 3: Make Cross-Artifact Consistency a First-Class Gate

**EPIC insight:** Individually good documents can disagree with one another.

**CaTDD action:**

Extend the review gates with a semantic-delta matrix:

| Source obligation | Story | Guide | Architecture | Detail design | Discovery ledger | US/AC/TC | Code/evidence |
| --- | --- | --- | --- | --- | --- | --- | --- |
| R-01 | preserved | preserved | refined | ... | TP-01 | TC-03 | passing |

Each transformation must be classified as:

- `PRESERVED`: meaning is unchanged.
- `REFINED`: intent is narrowed or decomposed with explicit rationale.
- `REFERRED`: intentionally assigned to another owner.
- `EXCLUDED`: explicitly out of scope with approval.
- `DIVERGED`: conflict requiring rework.
- `UNKNOWN`: missing evidence requiring a question.

This is the upstream complement to CaTDD's existing TP/TC traceability.

### Refinement 4: Distinguish Core, Risk-Triggered, and Advisory EPIC Practices

**EPIC insight:** Practitioner ratings varied by practice and context. The study
supports incremental adoption rather than universal, equal-weight ceremony.

**CaTDD action:**

Create three applicability tiers:

| Tier | Application |
| --- | --- |
| Core | Apply to nontrivial stories: clarification, outcomes, scope, verification, IDs, consistency |
| Risk-triggered | Apply for security, concurrency, migration, hardware, external dependencies, or irreversible boundaries |
| Advisory | Useful for documentation and comprehension but not normally allowed to block a simple reversible change |

Hard blockers should follow risk. A trivial documentation-only story should not
need the same artifact ceremony as a safety-critical migration.

### Refinement 5: Record Specification Quality Debt

**EPIC insight:** A dimension can be partially satisfied or not applicable; silence
should not collapse all states into pass or fail.

**CaTDD action:**

Maintain EPIC debt records alongside implementation gaps:

```text
EPIC-01 | E1.4 | partial | AC uses should/must inconsistently
        | owner=product | trigger=before implementation | status=open

EPIC-02 | I2.1 | gap | "session" and "conversation" used with different meanings
        | owner=architecture | trigger=before design approval | status=open
```

Debt does not automatically block every phase. It must carry:

- Severity.
- Affected obligations.
- The latest safe phase at which it must be resolved.
- A named owner.
- Evidence that closes it.

This makes quality trade-offs visible without turning EPIC into 40 unconditional
review checkboxes.

### Refinement 6: Add Completion Conditions to the Specification, Not Only the Workflow

**EPIC insight:** Verification completeness and readiness must be stated as part
of the specification.

**CaTDD action:**

For each significant story or quality obligation, record:

- Required evidence.
- Required environments.
- Required test levels.
- Required review gates.
- Conditions that mean "not done."
- Conditions that may be deferred without changing the current acceptance claim.

CaTDD already has `ready_for_implementation` and review verdicts. The refinement
is to make the **definition of done specific to the story**, not inferred solely
from a generic flow checklist.

## 8. Beyond EPIC: Deeper Insights for CaTDD

### 8.1 Testability Is Necessary but Not Sufficient

This is the most important implication of the comparison.

CaTDD currently requires every AC to be convertible into a testable obligation.
That prevents vague criteria from entering test implementation. It does not prove
that the AC set is complete, correctly scoped, terminologically consistent, or
consistent with the plan.

Therefore:

> CaTDD should gate both executable adequacy and specification sufficiency.

A story should not proceed merely because "this AC has a TC." It should also show
that the artifact set preserved the relevant intent.

### 8.2 Specification Quality Is a Conservation Property Across Transformations

EPIC describes a set of quality dimensions. A deeper operational formulation is that
each obligation must be preserved across transformations:

```text
business intent
  -> story
  -> AC
  -> design constraint
  -> test point
  -> test case
  -> code behavior
  -> runtime evidence
```

At each transition, an obligation may be preserved, refined, split, referred, or
explicitly excluded. It must not silently disappear or change meaning.

Call this the **Transformation Preservation Property**:

> For every material obligation, the transformation from source intent to
> executable evidence either preserves its meaning or records a visible,
> approved change of meaning.

This adds a dynamic dimension that EPIC, as a mostly static rubric, does not fully
address. CaTDD's TestEvidenceChain already approximates it downstream; extending
the property upstream would make it a complete artifact-set invariant.

### 8.3 Specification Debt Precedes and Can Mask Test Debt

CaTDD already exposes `GAP`, `QUESTION`, `EXCLUDED`, and unlinked test points. EPIC
shows that specification debt can exist before those states are visible.

Examples:

- Every AC has a TC, but two ACs describe the same obligation differently.
- Every scenario is testable, but the non-goals omit a platform the plan silently
  supports.
- The detail design names an interface, but the story never defines who owns its
  lifecycle.
- A plan task is complete, but it implements a technology choice not justified by
  the specification.

These are not test failures. They are **pre-test specification debt**. CaTDD needs
a place to record them without falsely marking a test point as a GAP or a question
as a product blocker.

### 8.4 EPIC Measures Declarative Sufficiency; CaTDD Must Still Evaluate Engineering
Soundness

An artifact can be sufficiently explicit and still describe a poor architecture,
an unsafe security policy, or the wrong product decision. EPIC does not establish
that the stated intent is wise.

CaTDD must preserve separate lenses:

- **Specification sufficiency**: is the intent clear and coherent?
- **Architecture validity**: is the chosen structure appropriate?
- **Implementation quality**: does the code satisfy the obligations safely?
- **Operational evidence**: does the deployed system actually behave as claimed?

A high EPIC score is not an architecture approval.

### 8.5 The Specification Itself Needs a Fitness Function

The earlier architecture analysis recommended executable governance. EPIC supplies
candidate properties that can be checked mechanically or semi-mechanically:

- Every referenced ID resolves.
- Every story scope item appears in a downstream obligation or explicit exclusion.
- Every material AC has a verification method and completion condition.
- Every quality scenario has a threshold or exact predicate.
- Every normative term belongs to the controlled vocabulary.
- Every changed requirement has an explicit delta classification.
- Every `SUPERSEDED` decision or withdrawn requirement remains discoverable.
- Every `QUESTION` has an owner and a latest-resolvable phase.

This turns EPIC from a post-hoc rubric into a **specification fitness function**.
It is more valuable than a static score because it detects drift as artifacts
change.

### 8.6 Ambiguity Should Be Classified by Resolution Path

`ONE-MORE-THING` is a strong safety invariant, but implementation benefits from
knowing why the process stopped. EPIC's distinction between an unresolved marker
and a settled requirement suggests a richer taxonomy:

| Ambiguity type | Correct action |
| --- | --- |
| Source-resolvable | Read the authoritative artifact and continue without asking |
| Policy-resolvable | Escalate to the decision owner; do not infer |
| Scope-resolvable | Record an explicit exclusion or referral with approval |
| Execution-resolvable | Record a verification limitation without changing intent |
| Irreducibly ambiguous | Stop with `ONE-MORE-THING` |

This preserves CaTDD's no-guess rule while avoiding unnecessary questions when a
known source already settles the issue.

### 8.7 EPIC Is a Quality Compass, Not a Participation Trophy

The paper reports that a majority of practitioners endorsed every practice, but
the ratings were not uniform. Lower ratings exposed real trade-offs:

- Detailed delivery planning can be premature.
- Exhaustive traceability can create reading cost.
- Some agents can resolve some gaps in context.
- Some practices matter more as projects grow.

CaTDD should therefore optimize for **correctness per unit of specification
effort**, not maximum EPIC coverage.

The useful question is not:

> Did we satisfy all forty practices?

It is:

> Which of the material risks in this story are currently protected by explicit,
> consistent, verifiable intent, and which are merely assumed?

### 8.8 EPIC Completes the "Why" of Test-First Development

TDD explains how to turn a known obligation into an executable check. EPIC explains
why the obligation itself may still be insufficient.

Together:

```text
EPIC: make intent sufficiently explicit and coherent
CaTDD: make intent testable and evidenced
RED/GREEN: prove implementation against executable intent
Review gates: prevent unsupported transition to the next lifecycle phase
```

This is a stronger AI-native methodology than either framework alone: EPIC protects
the meaning of the specification; CaTDD protects the integrity of execution.

## 9. Proposed CaTDD Control Model

The following model integrates EPIC without duplicating the existing CaTDD
methodology.

### 9.1 Gate Placement

| Lifecycle point | EPIC contribution | CaTDD owner |
| --- | --- | --- |
| Intent clearing | Unambiguity, scope, product/implementation separation | `SPEC_clearStoryIntent` |
| Requirement review | E/P/I dimensions, terminology, completion conditions | `SPEC_reviewUserStory` |
| Architecture review | Cross-artifact consistency, constraints, dependencies | `SPEC_reviewArchDesign` |
| Detail-design review | Technical context, data model, traceability, testability | `SPEC_reviewDetailDesign` |
| Test design | Verification scenarios, methods, completion evidence | `SPEC_designTests` / discovery gate |
| Implementation review | Requirements-to-code traceability and drift | `SPEC_reviewProductCodes` |
| Closure | Whole artifact-set sufficiency and unresolved debt | `SPEC_closeUserStory` |

### 9.2 Gate Formula

Do not replace existing verdicts with an aggregate EPIC score. Use a compound
readiness predicate:

```text
ready =
  no unresolved blocking QUESTION
  AND no undispositioned in-scope GAP
  AND required EPIC dimensions are satisfied or explicitly risk-accepted
  AND TestEvidenceChain is unbroken for the declared scope
  AND required review gates are PASS
```

The EPIC portion is evidence, not an independent authority over CaTDD's safety
rules.

### 9.3 Three-Tier Adoption

#### Tier A: Core Gate

Implement first:

- Clarification-seeking.
- Measurable outcomes.
- Explicit scope and verification boundaries.
- Stable identifiers.
- Cross-artifact consistency.
- Requirements-to-implementation traceability.
- Testable completion conditions.

These correspond to the highest-risk failure modes and already have strong CaTDD
support.

#### Tier B: Risk-Triggered Gate

Require when the story touches:

- Security or privacy.
- External dependencies and distributed state.
- Concurrency or lifecycle transitions.
- Data migration or compatibility.
- Hardware or operational constraints.
- Irreversible architecture boundaries.

Add:

- Dependency verification and failure-mode handling.
- Technical/operational constraints.
- Data/interface evolution.
- Cross-document navigation and implementation planning.

#### Tier C: Advisory/Quality Improvement

Use for:

- Atomic wording of every subordinate statement.
- Uniform notation for every artifact type.
- Strongly consistent document organization.
- Additional comprehension examples.

Record them as improvement debt when they do not threaten current acceptance.

## 10. Actionable Evolution Roadmap

### Phase 1: Establish the Quality Lens

1. Add an `EPIC Specification Sufficiency` ledger to the story or TASKS artifact.
2. Add controlled terminology and normative-language guidance to
   `projectContext.md` or a dedicated glossary.
3. Define the transformation dispositions: `PRESERVED`, `REFINED`, `REFERRED`,
   `EXCLUDED`, `DIVERGED`, `UNKNOWN`.
4. Add an artifact-set trace matrix to the review gates.

### Phase 2: Strengthen the Gates

1. Extend `SPEC_reviewUserStory` with E/P/C sufficiency checks.
2. Extend `SPEC_reviewDetailDesign` with cross-artifact consistency and explicit
   data/interface evolution checks.
3. Extend `SPEC_closeUserStory` to verify that specification debt is resolved,
   accepted, or routed.
4. Update review examples to show:
   - A testable but over-scoped AC.
   - A consistent-looking artifact with semantic drift.
   - A plan that implements an unapproved design choice.
   - A correct implementation with an unresolved terminology ambiguity.

### Phase 3: Add Fitness Functions

Add checks, preferably as deterministic scripts or review assertions:

- Resolve all referenced artifact IDs.
- Detect duplicate or orphaned requirement IDs.
- Detect requirements without verification methods or completion predicates.
- Detect scope entries that never reach an obligation or an explicit exclusion.
- Detect changed upstream requirements whose downstream evidence is stale.
- Flag ambiguous modal words and terminology drift.
- Verify that every high-risk obligation has a fitness function or evidence owner.

### Phase 4: Evaluate Rather Than Assume

Before making EPIC checks universal blockers:

1. Pilot on several story types: small CLI change, architectural change,
   concurrent/stateful change, quality-only change, and security-sensitive change.
2. Measure review rework, false blocking, missed ambiguity, and artifact-reading
   cost.
3. Compare CaTDD outputs with and without the EPIC gate.
4. Preserve evidence of which practices prevent actual defects or rework.

This mirrors EPIC's own lesson: evaluate practices in use, not only by their
theoretical appeal.

## 11. Risks and Anti-Patterns

### 11.1 Turning EPIC into Forty Mandatory Checkboxes

This would produce documentation volume without proportional risk reduction. Use
the tiered model and explicit non-applicability.

### 11.2 Treating an EPIC Score as Truth

An aggregate score hides which dimension failed and whether the failure matters.
Prefer IDs, evidence, dispositions, and owners over a single number.

### 11.3 Overwriting Product Intent with Implementation Decisions

Technical constraints may legitimately belong in the specification when they are
required behavior. The test is not "no technical content"; it is whether the
product requirement remains recognizable and traceable.

### 11.4 Reporting Documentation Quality as Runtime Quality

Specification sufficiency does not prove implementation correctness, safety,
performance, or deployment success. Keep evidence classes separate.

### 11.5 Using EPIC to Bypass `ONE-MORE-THING`

A rubric cannot authorize an assumption. An unresolved policy decision remains a
human decision unless an authoritative source already settles it.

### 11.6 Reusing the Same Test Wording as the Specification

If ACs, TPs, and test names are copied mechanically from an incomplete source, all
artifacts can agree while preserving the same omission. EPIC's singularity and
comprehension checks should encourage independent review, not phrase duplication.

## 12. Synthesis: CaTDD as the Execution System Around EPIC

| Dimension | EPIC | CaTDD |
| --- | --- | --- |
| Core question | Is the artifact set clear enough to implement safely? | Is intent converted into traceable evidence? |
| Primary value | Artifact quality vocabulary and empirical grounding | Test-first execution and lifecycle enforcement |
| Strength | Upstream completeness, normativity, consistency | Test depth, RED evidence, runtime proof, bounded workflow |
| Limitation | No control loop; scores are not proof | Local gates may miss holistic specification gaps |
| Best integration | Pre-execution sufficiency evidence | Gate consumption, rework routing, and evidence preservation |

The most defensible conclusion is:

> EPIC supplies the missing evaluation layer above CaTDD's verification layer.

CaTDD already implements most EPIC practices in operational form. The high-value
evolution is to make their artifact-set relationship explicit, to standardize
normative terminology, and to measure specification quality as a living property
rather than a one-time document review.

The resulting methodology is not "EPIC vs. CaTDD" but:

```text
EPIC specification sufficiency
  -> CaTDD test-point discovery
  -> comment-alive US/AC/TC design
  -> semantic RED/GREEN implementation
  -> runtime and review evidence
  -> closure with explicit residual risk
```

That combination preserves EPIC's strongest insight—an agent should not decide
what the specification failed to say—while retaining CaTDD's strongest guarantee:
the implementation should not advance without evidence that the stated obligation
has been verified.
